# 储值功能合规与资质说明（单用途商业预付卡）

**适用范围**：餐饮门店在微信小程序里向顾客发售「储值余额」并用它抵扣堂食消费。
**代码对应**：`backend/domain/po/wallet.go`、`backend/infrastructure/store/dao/wallet.go`、
`backend/application/service/wallet_service.go`、`frontend/apps/miniprogram/src/pages/wallet/*`
**上线硬前置**：本文第 0 节的清单全部打勾后，才能打开 `wallet_recharge_enabled`。

> **免责声明**：本文是工程侧的合规自查清单，**不是法律意见**。
> 法规条文以最新有效版本为准，具体义务还取决于门店的**主体性质**（企业法人 / 个体工商户）、
> **注册地**（多地有单用途卡的地方性法规）与**发卡规模**。
> 正式上线前请由法务或当地商务主管部门确认一遍；文中标注「需复核」的阈值与比例尤其如此。

## 1. 这件事在法律上是什么

餐饮门店的储值余额，法律性质是**单用途商业预付卡**：由商业企业发行、只在本企业或同一品牌
连锁企业内兑换商品或服务的预付凭证（含实体卡，也含以密码、串码、图形等为载体的虚拟卡）。

把它认成「预付卡」而不是「普通预收款」，带来一整套**额外义务**：

- 发卡备案（部分主体）
- 实名登记与单张限额
- 必须明示章程 / 协议
- 必须提供退卡服务
- 预收资金的使用限制与存管（部分主体）
- 定期报送预收资金余额（部分主体）

反过来说，若没把它当预付卡来做，最典型的两个事故就是
**超限额发卡**（单张记名卡超过 5000 元）与**拒绝退卡**（顾客要求退回余额被拒）。

### 1.1 主要法规依据

| 层级 | 文件 | 与本项目相关的部分 |
|---|---|---|
| 部门规章 | 《单用途商业预付卡管理办法（试行）》（商务部令 2012 年第 9 号） | 备案、实名、限额、明示、退卡、资金存管 |
| 法律 | 《消费者权益保护法》 | 第 26 条：不得以格式条款作出排除 / 限制消费者权利的规定 |
| 法律 | 《民法典》合同编 | 预付式消费的服务合同关系 |
| 法律 | 《个人信息保护法》 | 手机号属个人信息，收集须告知并取得同意，遵循最小必要 |
| 地方性法规 / 规章 | 各省市单用途预付消费卡管理办法（上海、北京、江苏等地均有） | 常比国家层面更严格（如七日无理由退卡、资金存管比例） |
| 税务 | 营改增后单用途卡的增值税处理规定 | 售卡（充值）环节不缴增值税、不得开专票；消费环节纳税开票（见 §8） |

## 2. 主体判断：是否需要备案

《办法》约束的是**企业法人**，按发卡形态分三类，备案机关与后续义务不同：

| 类型 | 定义要点（**阈值需复核**） | 备案机关 |
|---|---|---|
| 集团发卡企业 | 发行在本集团内使用的单用途卡 | 商务部（省级商务主管部门转报） |
| 品牌发卡企业 | 使用同一品牌、在境内外开展业务的企业集团 | 商务部 |
| 规模发卡企业 | 除上述两类外，上一会计年度营业收入 / 年末资产总额 / 注册资本达到规定规模的企业 | 省级商务主管部门 |

**判断步骤**：

1. 门店是否为**企业法人**（公司制）？个体工商户通常不在《办法》的「发卡企业」范围内，
   但仍受《消法》与地方条例约束，**且地方条例往往把个体户也纳入管理** ——
   不要因为「我是个体户」就认为没有任何义务。
2. 若是企业法人：开展单用途卡业务之日起 **30 日内**办理备案（具体时限以现行条文为准）。
3. 若为连锁品牌：通常由品牌方（品牌发卡企业）统一备案，加盟门店按品牌方规则执行。

> **工程侧结论**：备案与否不影响代码行为，但**影响额度参数能不能调高**。
> 系统出厂即按最严格口径（不记名 1000 / 记名 5000），门店只有在确认自己已完成相应备案后，
> 才应在「系统配置 → 储值」里上调这些上限。

## 3. 实名登记与限额

### 3.1 限额（系统在代码里强制）

《办法》第十八条（**需复核**）：**单张记名卡限额不超过 5000 元，单张不记名卡限额不超过 1000 元。**

| 配置项 | 默认 | 含义 |
|---|---|---|
| `wallet_balance_max` | 1000 | 未记名账户余额上限（元） |
| `wallet_balance_max_named` | 5000 | 已记名账户余额上限（元） |
| `wallet_recharge_min` / `wallet_recharge_max` | 1 / 1000 | 单笔充值区间（元，只收整数元） |

判定「记名」的口径：**是否绑定手机号**（`tb_customer_identity.provider='phone'`）。
校验在 `service.CreateWalletRecharge` 里做，且**本金 + 赠金合并计算** ——
只算本金会让赠金多的会员突破监管上限。

### 3.2 实名（系统提供能力，门店决定强度）

| 配置项 | 默认 | 行为 |
|---|---|---|
| `wallet_realname_required` | `1` | 为 `1` 时，未绑手机号的会员点充值会被拒绝并提示去「我的」绑定 |

- 手机号通过小程序 `getPhoneNumber` 按钮获取，`code` 由后端换号码后只存
  `tb_customer_identity`，接口一律返回脱敏号（`139****0001`）。
- 严格意义上的「实名登记」要求的是**有效身份证件**信息。仅绑手机号是否满足，
  取决于地方主管部门口径（多数线上场景以手机号为实名载体，但**需与主管部门确认**）。
- 《办法》另有「一次性购买（充值）1 万元（含）以上不记名卡应登记身份信息」的规定（**需复核**）。
  默认单笔上限即为 1000 元，天然不会触发；若门店调高单笔上限，必须同步复核。

### 3.3 有效期

《办法》第十九条（**需复核**）：记名卡不得设有效期；不记名卡有效期不得少于 3 年。

系统落点：**储值余额不设有效期**，永久有效。这句话写进了出厂规则文案，
也是门店自行编辑规则时**不得删改**的条款。

## 4. 明示义务：《储值规则》必须写什么

发卡企业应向购卡人公示章程 / 协议。系统把它落成一个可编辑的配置项 + 一次强制确认：

- **配置项**：`wallet_rules_text`（正文）、`wallet_rules_version`（版本号）
- **展示**：小程序「我的钱包」页常驻展示；未同意时充值区只显示规则全文与「阅读并同意」
- **留痕**：`POST /customer/wallet/rules/agree` 写 `tb_wallet_agreement`
  （会员 ID + 规则版本 + 同意时间）

**五项必备条款**（出厂默认文案已全部覆盖，门店编辑时不得删除）：

1. **适用范围**：仅限本店堂食消费抵扣，不找零、不兑现、不计息、不可转赠；
2. **有效期**：不设有效期（发行不记名卡时有效期不得少于 3 年）；
3. **限额与实名**：不记名 / 记名的余额上限各是多少，如何完成实名；
4. **退卡退款**：本金可退、赠金不退，退卡办理途径；
5. **查询凭证**：顾客可随时查询余额与流水，门店完整保存流水。

**改文案必须改版本号**：版本号变化会让已同意过的会员重新确认，
这是「他充值时看到的是哪一版」的唯一留痕依据。

## 5. 退卡与退款

### 5.1 顾客的预付款必须拿得回去

这是最容易出事、也最容易被忽略的一条。系统在三个位置保证它：

| 场景 | 路径 | 代码 |
|---|---|---|
| 订单退款（余额支付的订单） | 原路退回储值本金 | `service.WalletRefundForOrder` |
| 订单退款（余额 + 微信混合支付） | **按支付流水分摊**：微信那部分原路退回微信，储值部分退回钱包（赠金不退） | `service.CreateRefundParts` |
| 顾客要求退卡 / 退余额 | 后台「退余额」：本金清零 + 赠金作废，门店线下付款 | `service.AdminWalletWithdraw` |
| 注销会员 | 余额未清零时**拒绝注销**，提示先退余额或继续消费 | `dao.DeleteCustomerAccount` |

退余额会写审计（`储值管理 / 退余额`）与一条 `withdraw` 流水，金额与门店实际付款对得上。

### 5.2 赠金不退（本金与赠金分桶的原因）

- **本金**（`tb_wallet.balance`）：顾客真金白银充进来的钱，可退；
- **赠金**（`tb_wallet.balance_gift`）：充值赠送 / 活动赠送 / 后台赠送，可消费、**不可退现**。

**为什么要分桶**：混在一个数字里，退余额时无法回答「这笔钱该不该退给顾客」，
只能一刀切全退 —— 于是「充 100 送 10 → 用赠金买单 → 退款拿回本金」可以无限套现。

**扣减顺序**：消费时先扣赠金、再扣本金（`dao.splitDelta`），流水里记下赠金占比
（`tb_wallet_txn.gift_amount`）；退款时据此算出可退本金的上限，
超过上限会被拒绝并提示「含赠金 X 元（赠金不退），最多可退本金 Y 元」。

### 5.3 七日无理由退卡（地方性要求）

部分地区（如上海）规定了**付款之日起七日内未消费的可要求全额退款**。
这类要求高于国家层面，门店应按属地口径执行；系统层面不限制退余额的时点与次数，
只要门店愿意退，随时可操作。

## 6. 微信侧资质与平台规则

这一节不是代码能解决的，但**不做完就不能上线储值充值**：

| # | 事项 | 说明 |
|---|---|---|
| 1 | 微信支付商户号经营类目 | 必须与「餐饮」一致；涉及预付卡销售的，按微信支付要求补充相应资质 |
| 2 | 小程序服务类目 | 小程序后台填写的类目需与实际提供的服务一致；涉及预付卡 / 虚拟卡的类目通常需额外资质材料 |
| 3 | JSAPI 支付 | 储值充值走 JSAPI，要求 `wxpay_appid` 为**小程序** AppID 且已配 `wx_app_secret` |
| 4 | `getPhoneNumber` 权限 | 需在小程序后台申请该接口权限；通常要求企业主体，**按次收费** |
| 5 | 平台运营规范 | 遵守《微信小程序平台运营规范》关于预付式消费、资金与退款的条款；不得诱导充值、不得设置不可退的格式条款 |

> 微信侧的类目与资质审核口径会调整，以上为自查方向；
> 具体以微信支付商户平台与小程序后台的实际要求为准（另见 [`../wechat-config.md`](../wechat-config.md)）。

## 7. 个人信息保护

| 信息 | 收集方式 | 用途 | 合规要点 |
|---|---|---|---|
| 微信 openid | `wx.login` 静默换取 | 会员身份、JSAPI 支付的 `payer.openid` | 已在隐私保护指引声明 |
| 手机号 | `getPhoneNumber` 按钮（用户主动触发） | 实名登记、提高余额上限 | 需在隐私保护指引补充声明；仅存身份表，接口只回脱敏号 |
| 储值流水 | 系统自动记录 | 顾客的查询凭证、门店对账 | 属经营数据，随会员注销一并删除 |

要点：

- 手机号属个人信息，收集前须**告知并取得同意**；绑定是**自愿**的，
  不绑不影响点餐，只影响能否充值与余额上限（`wallet_realname_required` 可关）。
- 完整号码**不下发**到任何前端（列表 / 详情一律脱敏），后端日志也只打脱敏号。
- 会员注销时，档案、登录方式、储值账户、规则同意记录**一并物理删除**；
  历史订单保留（门店经营数据）但归属置 0。

## 8. 财务与税务口径

### 8.1 收入确认时点（系统已按此落账）

- **充值**：顾客的预付款，是**负债**不是收入 → 不计入营业额；
- **消费**：用余额支付订单时才确认收入 → 计入当日营业额；
- **退款**：冲回收入，按退款发生日扣减。

系统落点：营业额统计只查 `tb_order`（见 `dao.RangeAmount`），`tb_recharge` 从不参与。

### 8.2 「营业额」里要拆出储值核销

消费当天确认收入，但**没有现金流入**（钱在充值那天就收过了）。
所以报表把两个口径分开（管理端「今日营业额」主卡下方一行）：

```
今日营业额 8000.00
其中储值核销 3000.00 · 实际到账 5000.00
```

对应字段：`Summary.TodayWalletAmount` / `Summary.TodayCashAmount`，
底层是 `dao.RangeWalletConsume`（与 `RangeAmount` 同口径，只多 `pay_channel='wallet'`）。

### 8.3 发票

按现行营改增口径（**需财务复核**）：售卡（充值）环节不缴纳增值税、不得开具增值税专用发票；
持卡人实际消费时由销售方缴纳增值税并可开票。

系统侧可支撑：充值流水（`tb_recharge`）与消费流水（`tb_wallet_txn` 的 `consume`）
各自完整，能回答「这笔消费对应哪次充值」。

| 注销前清零 | 余额未清零拒绝注销 | `dao.DeleteCustomerAccount` |

| 回调不丢钱 | 充值单主动查单补账（回调丢失时自救） | `handler.WalletRechargeReconcile` |
| 回调不重复加钱 | 先抢占（条件更新 0→1）再动钱；并发回调里只有一个入账，其余按幂等成功 | `service.WalletRechargeCredit` |
| 废单不误入账 | 超时未支付单关闭，关闭后回调拒绝入账 | `dao.ExpirePendingRecharges` / `ErrRechargeClosed` |

## 10. 门店运营侧的注意事项

1. **不要诱导充值**：大额充值话术、「充得多送得多」的强推销，本身就是监管关注点；
2. **规则文案不要自己加「概不退还」**：这是《消法》第 26 条明令禁止的无效格式条款；
3. **赠金要有边界**：赠金可设使用门槛或不参与的活动，但必须在规则里写清；
4. **定期自查余额上限**：如果门店把 `wallet_balance_max` 调高过，
   请确认当时依据的备案 / 属地规定仍然成立；
5. **留好退卡的付款凭证**：系统只记录「清零了多少」，实际付款的收据由门店保管。
